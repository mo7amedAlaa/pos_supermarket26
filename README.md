# نظام نقاط بيع (POS) لسوبر ماركت — MERN Stack

نظام كامل لإدارة سوبر ماركت:
- **الأدمن**: يضيف/يعدّل المنتجات، يدير المخزون والجرد (إضافة كمية أو تصحيح الكمية بعد الجرد الفعلي)، يدير الفئات والمستخدمين (أدمن/كاشير)، ويطّلع على تقارير المبيعات.
- **الكاشير**: يبيع المنتجات عن طريق مسح الباركود/QR (بجهاز سكانر فعلي أو كاميرا)، يطبع فاتورة لكل عملية بيع، والمخزون يتحدث تلقائيًا مع كل عملية بيع.

## البنية

```
pos-supermarket/
  backend/     Node.js + Express + MongoDB (Mongoose)
  frontend/    React (Vite) + React Router
```

## التشغيل

### 1) المتطلبات
- Node.js 18+
- MongoDB (محلي أو MongoDB Atlas)

### 2) الباك اند
```bash
cd backend
npm install
cp .env.example .env
# عدّل MONGO_URI و JWT_SECRET في .env حسب بيئتك
npm run dev        # أو: npm start
node seed.js        # ينشئ حساب أدمن افتراضي: admin / admin123 (غيّر كلمة المرور بعد أول دخول)
```
السيرفر يعمل افتراضيًا على `http://localhost:5000`.

### 3) الفرونت اند
```bash
cd frontend
npm install
npm run dev
```
يعمل على `http://localhost:5173` وموجّه (proxy) على `/api` إلى السيرفر تلقائيًا (انظر `vite.config.js`).

### 4) تسجيل الدخول
- افتح `http://localhost:5173`
- سجّل دخول بحساب الأدمن الافتراضي: **admin / admin123**
- من "المستخدمون" أضف حسابات كاشير لموظفيك.

## الباركود / QR — طريقتان مدعومتان
1. **جهاز سكانر فعلي (USB أو Bluetooth)**: يعمل تلقائيًا في صفحة "المنتجات" (عند فتح فورم الإضافة) وصفحة "الكاشير" بدون أي إعداد — لأن أغلب أجهزة السكانر تعمل كلوحة مفاتيح (Keyboard Wedge) وتكتب الكود بسرعة ثم Enter، والنظام يلتقطها تلقائيًا.
2. **الكاميرا**: زر "مسح بالكاميرا" يفتح الكاميرا (موبايل/لابتوب) ويقرأ QR أو الباركود مباشرة، مفيد لو مفيش جهاز سكانر متاح.

## طباعة الفاتورة
بعد إتمام البيع تظهر الفاتورة في نافذة منبثقة، زر "طباعة" يفتح نافذة طباعة مخصصة لحجم إيصال الكاشير (Receipt)، ويمكن توصيلها لاحقًا بطابعة حرارية عادية تعمل كطابعة نظام (Windows/Linux printer driver) بدون أي كود إضافي.

## الجرد (Inventory Count)
من صفحة "المنتجات والمخزون":
- **إضافة كمية**: لتوريد بضاعة جديدة (stock in).
- **جرد (تصحيح الكمية)**: تدخل الكمية الفعلية اللي عددتها بنفسك في المخزن، والنظام يحسب الفرق تلقائيًا ويسجله في سجل الحركة (StockLog) مع اسم من قام بالتعديل والتاريخ — عشان يبقى عندك تتبع كامل لأي فروقات.

## ملاحظات أمنية قبل الإنتاج
- غيّر `JWT_SECRET` و كلمة مرور الأدمن الافتراضية فورًا.
- فعّل HTTPS خلف الخادم (nginx/Caddy) قبل النشر الفعلي.
- اعمل نسخ احتياطي دوري لقاعدة بيانات MongoDB.

# التحديث: دعم السوبر ماركت الحقيقي

تمت إضافة 3 مميزات أساسية عشان النظام يناسب سوبر ماركت أكل وشرب فعلي.

## 1) باركود الميزان (المنتجات بالوزن)

الجبنة واللحمة والخضار مالهاش باركود ثابت — الميزان بيطبع باركود مدمج فيه الوزن:

```
2 0 | 1 2 3 4 5 | 0 1 2 5 0 | 7
----   ---------   ---------   -
بادئة   كود الصنف   الوزن جرام  checksum
```

**الإعداد:**
1. في `.env` اضبط `SCALE_BARCODE_PREFIXES` (خد أول رقمين من عينة باركود من ميزانك) و `SCALE_EMBEDDED_VALUE` (`weight` أو `price`).
2. عند إضافة منتج، فعّل **"منتج يُباع بالوزن"** وأدخل **كود الصنف في الميزان** (نفس الكود المبرمج على الميزان).
3. سعر البيع اللي بتدخله بيبقى **سعر الكيلو**.

**النتيجة:** الكاشير يمسح باركود الميزان → النظام يعرف الصنف والوزن ويحسب السعر أوتوماتيك. كل مسح = سطر منفصل بوزنه الخاص.

> النظام بيفرّق تلقائيًا: باركود بادئته 20-29 = ميزان، أي باركود تاني = منتج مصنع عادي. اتأكدنا إن باركودات زي كوكاكولا (`5449...`) والمنتجات المصرية (`622...`) بتتقري صح كمنتجات عادية.

## 2) الكرتونة مقابل القطعة

عند إضافة منتج معبأ، أدخل **عدد القطع في الكرتونة** (مثال: كرتونة شيبسي = 24).

عند التوريد، اضغط **"توريد"** واختار الإدخال بالكراتين:
- `3 كراتين + 5 قطع سايبة` → النظام يحسبها **77 قطعة** ويعرضها قدامك قبل الحفظ.
- سجل الحركة بيسجل التفاصيل: `(3 كرتونة × 24 + 5 قطعة)`.

## 3) تاريخ الصلاحية + الدفعات (Batches)

فعّل **"تتبّع تاريخ الصلاحية"** على المنتج. بعدها:

- كل **شحنة توريد** بتتسجل كدفعة منفصلة ليها **تاريخ صلاحية** و**سعر شراء** خاص بيها.
- البيع بيخصم بنظام **FEFO** (First Expired First Out) — الأقرب انتهاءً يتباع الأول.
- ده بيحل كمان مشكلة **تغيّر سعر الشراء بين الشحنات**: كل بيعة بتحسب تكلفتها الحقيقية من الدفعة اللي اتخصمت منها، فالأرباح بقت دقيقة.

**صفحة "تواريخ الصلاحية"** في لوحة التحكم بتعرض:
- الدفعات المنتهية بالفعل (اسحبها من الرف)
- الدفعات اللي قربت تنتهي (فلتر 7/15/30/60/90 يوم)

## حساب الأرباح

الفاتورة دلوقتي بتسجل `totalCost` و `profit` الفعليين، وصفحة التقارير بتعرض **أرباح اليوم** وربح كل فاتورة.

## ملاحظة للترقية من النسخة القديمة

لو عندك بيانات قديمة، المنتجات الموجودة هتشتغل عادي (`unitsPerCarton=1`, `trackExpiry=false`). فعّل المميزات على كل منتج من زر "تعديل" وقت ما تحتاجها.

# التحديث: الاستحمال المتزامن (Concurrency) + Realtime

## 1) حماية من تعارض البيع المتزامن

**المشكلة اللي كانت موجودة:** لو كاشيرين ضغطوا "إتمام البيع" على نفس المنتج في نفس اللحظة بالظبط، فيه احتمال (نادر لكن وارد) إن الاتنين يبيعوا كمية أكبر من المتاح فعليًا.

**الحل:** كل عملية بيع دلوقتي بتتلف بمعاملة MongoDB (transaction) مع **إعادة محاولة تلقائية** لو حصل تعارض كتابة (Write Conflict) — وده الـ pattern الرسمي الموصى بيه من MongoDB نفسها. لو كاشيرين حاولوا يبيعوا نفس المنتج في نفس اللحظة:
- المعاملة الأولى بتنجح عادي.
- التانية بتتكرر تلقائيًا (لحد 6 مرات) وتقرأ الكمية المُحدَّثة، فمفيش بيع "وهمي" لكمية مش موجودة.

**تم اختبار المنطق فعليًا** (`node scripts/testTransactionRetry.js`) بمحاكاة تعارض كتابة حقيقي، والنتيجة: إعادة المحاولة، commit/abort الصحيحين، والتوقف بعد حد أقصى من المحاولات بدل التكرار اللانهائي.

كمان تم تكبير الـ connection pool مع MongoDB (`maxPoolSize`) عشان السيرفر يقدر يخدم عدة طلبات متزامنة من عدة شاشات كاشير من غير ما يستنى.

## 2) Realtime عبر Socket.io

أي تغيير في المخزون أو فاتورة جديدة بيوصل **فورًا** لكل الشاشات المفتوحة من غير Refresh:

| الحدث | مين بيستقبله | بيعمل إيه |
|---|---|---|
| `invoice:created` | لوحة التقارير + كل الشاشات | تحديث الإحصائيات وسجل الفواتير فورًا، وتنبيه (toast) للكاشير التانيين |
| `stock:changed` | صفحة المنتجات | تحديث جدول المخزون فورًا لو أي حد غيّر كمية |
| `stock:low` | كل الشاشات | تنبيه فوري لما منتج يوصل لحد النقص |
| `product:created` / `product:changed` / `product:deleted` | صفحة المنتجات | تحديث القائمة فورًا |

**تم اختباره فعليًا** بسيرفر وعميل حقيقيين (مش بس نظريًا): عميل Socket.io اتصل، استقبل حدث `invoice:created`، والنتيجة وصلت في أقل من نص ثانية.

### الإعداد

في `.env` أضف (اختياري، للإنتاج فقط):
```dotenv
CORS_ORIGIN=https://your-frontend-domain.com
```

في الفرونت اند، لو السيرفر مش شغال على `localhost:5000`، أضف ملف `.env` جوه `frontend/`:
```dotenv
VITE_SOCKET_URL=https://your-backend-domain.com
```

## ملاحظة عن التوسّع لاحقًا (Scaling)

لو المحل كبر لعدة فروع أو حركة بيع كبيرة جدًا:
- **PM2 cluster mode**: لتشغيل السيرفر على أكتر من CPU core. محتاج وقتها Redis adapter لـ Socket.io عشان الأحداث توصل لكل الـ instances (`@socket.io/redis-adapter`) — قولّي لو وصلت للمرحلة دي وهضيفها.
- **MongoDB replica set / Atlas**: أنت بالفعل شغال على Atlas، فالـ transactions شغالة صح من غير أي إعداد إضافي.

# التحديث: احترافية وجاهزية للإنتاج + توليد الباركود

## 1) تحصين الباك اند للإنتاج

- **Helmet**: حماية من هجمات شائعة عبر HTTP headers (XSS, clickjacking, إلخ).
- **Rate limiting**: 10 محاولات دخول كحد أقصى كل 15 دقيقة (حماية من brute force)، و300 طلب/دقيقة عام لكل IP.
- **Compression**: ضغط الردود (gzip) لتحميل أسرع.
- **معالج أخطاء مركزي**: كل خطأ بيرجع كود HTTP ورسالة عربي واضحة حسب نوعه الفعلي (تعارض بيانات، معرّف غير صالح، إلخ) بدل "500" عامة لكل حاجة. **تم اختباره فعليًا** بسيرفر حقيقي (health check، 404، duplicate key، خطأ غير متوقع).
- **Graceful shutdown**: لو السيرفر اتقفل أو اتعاد تشغيله، بيسيب الطلبات الجارية تخلص ويقفل اتصال قاعدة البيانات بأمان بدل ما يقطعه فجأة.
- **نقطة فحص الصحة**: `GET /api/health` لأدوات المراقبة.
- **Pagination** لسجل الفواتير (`/api/invoices?page=1&limit=25`) - أداء أفضل مع نمو المحل.

## 2) أداء الفرونت اند

- **Code splitting**: كل صفحة أدمن وشاشة الكاشير في ملف JS منفصل بيتحمّل عند الطلب بس. النتيجة: الحزمة الرئيسية نزلت من **629KB لـ 268KB**، ومكتبتي الكاميرا (335KB) والباركود (66KB) بيتحمّلوا بس لما فعليًا تتفتح الميزة دي.
- **Debounce على البحث**: مبقاش كل حرف بتكتبه في خانة البحث يبعت طلب API لوحده.
- **Lazy loading + Suspense** لكل المسارات مع شاشة تحميل احترافية.

## 3) تجربة استخدام احترافية

- **Toast notifications** بدل `alert()` - إشعارات أنيقة تختفي تلقائيًا.
- **نافذة تأكيد مخصصة** بدل `confirm()` الافتراضية للمتصفح.
- **Error Boundary**: لو حصل خطأ غير متوقع في الواجهة، المستخدم يشوف شاشة استرداد بدل صفحة بيضا فاضية.
- **Loading states** واضحة في كل جدول وزرار حفظ.
- تحسينات بصرية عامة: ظلال، حركات انتقال، حالات hover/focus، إمكانية وصول أفضل بالكيبورد.

## 4) توليد باركود للمنتجات اللي مالهاش باركود

للمنتجات اللي مالهاش باركود من المصنع أصلًا (عيش بلدي، بقالة سايبة، منتج محلي الصنع):

1. من فورم "إضافة منتج جديد"، دوس **"توليد باركود"** بدل ما تمسح باركود موجود.
2. النظام بيولّد باركود **EAN-13 داخلي صالح** (بادئة `04` - رينج محجوز رسميًا في معيار GS1 للاستخدام الداخلي، فمش هيتعارض مع أي باركود حقيقي).
3. من جدول المنتجات، دوس **"الباركود"** على أي منتج عشان تشوف **ملصق قابل للطباعة فعليًا** (باركود حقيقي ممسوح، مش مجرد أرقام) مع اسم المنتج والسعر.
4. اختار عدد النسخ (لو محتاج تطبع ملصق لكل قطعة في الكرتونة) ودوس طباعة.

**تم اختبار خوارزمية التوليد فعليًا** مقابل باركودات حقيقية معروفة (كوكاكولا، منتج ألماني) للتأكد من صحة حساب رقم التحقق (checksum)، **وتم اختبار الرسم الفعلي** للباركود الناتج وتأكيد إن الأرقام المعروضة تحته تطابق الباركود المُدخل 100%.

**أمان التوليد المتزامن**: لو اتنين أدمن ضغطوا "توليد باركود" في نفس اللحظة، النظام بيستخدم عدّاد ذري (atomic counter) في قاعدة البيانات فمستحيل يطلعلهم نفس الرقم.

# التحديث: تعبئة/تقسيم منتج من خامة (Repackaging)

لمنتجات زي **الجبنة أو الأنشوجة** اللي بتشتريها سايبة وبتقسمها لأطباق بسعر وكمية ثابتين (مثال: طبق 50 جرام بـ10 ج.م، طبق 100 جرام بـ20 ج.م).

## الفكرة
- الخامة (الجبنة السايبة) منتج **موزون** عادي زي ما شرحنا قبل كده.
- كل حجم طبق (50 جم، 100 جم) هو منتج **مستقل** بسعر وكمية ثابتين، ومربوط بالخامة دي.
- لما تعبّي دفعة جديدة من الأطباق، النظام بيخصم الكمية المستخدمة من الخامة تلقائيًا **ويحسب تكلفة الطبق الواحد فعليًا** من سعر شراء الخامة الحقيقي (مش تخمين).

## الإعداد
1. أنشئ الخامة كمنتج موزون عادي (مثال: "جبنة رومي سايب").
2. أنشئ منتج الطبق كمنتج عادي (باركود مولّد أو ممسوح)، وفي فورم الإضافة فعّل **"المنتج ده مُعبّأ من خامة تانية"**، اختار الخامة، وحدد **الكمية المستهلكة لكل وحدة بالكيلو** (مثال: `0.05` لطبق 50 جرام).
3. من جدول المنتجات، دوس زرار **"تعبئة"** اللي بيظهر بس على المنتجات المربوطة بخامة، أدخل عدد الأطباق المراد إنتاجها، والنظام هيوريك مباشرة هل الخامة كفاية ولا لأ.
4. بعد التنفيذ: الخامة بتتخصم، الأطباق بتتضاف للمخزون، **وتكلفة الطبق بتتحدّث أوتوماتيك** حسب التكلفة الفعلية.

**تم اختبار حساب التكلفة والخصم فعليًا** بسيناريو مطابق لحالة الجبنة/الأنشوجة: تقسيم خامة لحجمين مختلفين من الأطباق من نفس المخزون، والتأكد من دقة الخصم التراكمي وحساب هامش الربح لكل حجم على حدة، وكمان اختبار رفض العملية لو الخامة مش كفاية.

هذا يحل مشكلتين مع بعض: **دقة المخزون** (الخامة السايبة بتتابع صح مع كل تعبئة) و**دقة الأرباح** (تكلفة كل طبق مبنية على السعر الحقيقي للخامة، مش سعر ثابت مكتوب يدويًا وممكن يبقى قديم).

# التحديث: تصميم شامل (Design System)

## الخطوط والأيقونات
- خط **Cairo** (من Google Fonts) - خط عربي احترافي بدل الخط الافتراضي للمتصفح.
- مكتبة **lucide-react** للأيقونات - كل زرار وعنوان صفحة وحالة فاضية بقى ليه أيقونة واضحة بدل النص المجرد.

## حالات موحّدة عبر كل الصفحات
- **Loading**: بدل السبينر البسيط، الجداول بتعرض **Skeleton rows** (خطوط رمادية متحركة) وهي بتحمّل - إحساس أكتر احترافية وأقرب لتطبيقات حقيقية.
- **Error handling**: أي صفحة فشل تحميلها بتعرض رسالة واضحة **مع زرار "إعادة المحاولة"** بدل ما تفضل فاضية بصمت. ده كان ناقص خالص قبل كده - أي فشل في الشبكة كان بيسيب الجدول فاضي من غير تفسير.
- **Empty states**: بدل "لا توجد بيانات" كنص عادي، كل صفحة بقى ليها شاشة فاضية بأيقونة ورسالة واضحة، وزرار إجراء مباشر لو مناسب (زي "أضف أول منتج").

## الألوان والحركة
- نظام ألوان موحّد (متغيرات CSS) بدل ألوان متفرقة في كل مكان.
- حركات دقيقة: الصفحات بتظهر بـ fade-in، المودالز بتنبثق بحركة طبيعية، الـ toasts بتنزلق، عناصر السلة في شاشة الكاشير بتظهر بحركة سلسة.
- النظام **بيحترم تفضيل "تقليل الحركة"** في نظام التشغيل (`prefers-reduced-motion`) لمن يفضّل كده لأسباب صحية أو أداء.

## صفحة تسجيل الدخول
تصميم جديد بالكامل: أيقونة، حقول بأيقونات جانبية، وزرار إظهار/إخفاء كلمة المرور.

## ملاحظة فحص جودة
بعد إعادة بناء ملف الـ CSS بالكامل، تم عمل **مقارنة آلية** بين كل الكلاسات (classNames) المستخدمة فعليًا في كل ملفات React وكل الكلاسات المعرّفة في ملف الـ CSS، للتأكد من عدم وجود أي عنصر بدون تنسيق. تم اكتشاف وإصلاح حالتين ناقصتين (نافذة الكاميرا وتصميم الفاتورة المطبوعة) بهذه الطريقة.

# التحديث: تصفح المنتجات بدون الاعتماد على السكانر

زرار **"تصفح المنتجات"** جديد في شاشة الكاشير، بديل كامل للسكانر:

- شاشة كروت لكل المنتجات، مع بحث وفلترة بالفئة
- **منتج معبأ**: دوسة واحدة = يتضاف للسلة فورًا
- **منتج موزون**: دوسة على الكارت بتفتح حقل صغير لإدخال الوزن يدويًا (بديل لباركود الميزان لو مش متاح وقتها)
- تأكيد بصري سريع (✓ أخضر) بعد كل إضافة، والكارت بيتعطل تلقائيًا لو المنتج خلص من المخزون

مفيد لو الباركود مبهدل، أو مفيش سكانر فعلي متاح، أو الكاشير عايز يتأكد بعينه من المنتج قبل الإضافة.

**ملحوظة تقنية**: أثناء البناء، اكتُشف وأُصلح خلل حقيقي في تداخل عناصر HTML (زرار جوه زرار، وهو غير صالح في HTML ومسبب تصرف غير متوقع في المتصفح)، وكمان خلل في تسلسل أحداث لوحة المفاتيح كان ممكن يخلي الضغط على Enter لتأكيد الوزن يعيد فتح نفس الحقل بدل ما يقفله. الاتنين اتصلحوا وتم التأكد من نجاح البناء بعدهم.

# التحديث: خصم الخامة فورًا وقت إنشاء المنتج (مش خطوة منفصلة بعدها)

قبل كده، لما تنشئ منتج مربوط بخامة (زي "طبق جبنة 100 جم")، كنت لازم تعمل خطوتين: (1) إنشاء المنتج، (2) دوس "تعبئة" منفصلة بعدها لأول دفعة.

**دلوقتي الخطوتين بقوا واحدة**: لما تكتب "عدد الوحدات المراد إنتاجها الآن" في فورم الإضافة نفسه وتدوس "حفظ"، **النظام يخصم الكمية المطلوبة من الخامة فورًا وينشئ المنتج بالكمية دي في نفس اللحظة** — معاملة واحدة ذرية (atomic transaction): لو الخامة مش كفاية، العملية كلها بترفض ومفيش منتج ناقص أو خامة اتخصمت بالغلط.

زرار "تعبئة" لسه موجود ومستخدم لإنتاج **دفعات لاحقة** لمنتج موجود بالفعل.

**تم اختبار المنطق فعليًا** بنفس سيناريو حقيقي: 12 كيلو جبنة، إنتاج 50 طبق (100 جرام لكل واحد) وقت الإنشاء → تم التأكد من: الخصم الصحيح (12 - 5 = 7 كيلو متبقية)، حساب التكلفة الصحيح، وأهم حاجة: **رفض العملية بالكامل** (transaction rollback) لو الكمية المطلوبة أكبر من المتاح — تم اختبار محاولة إنتاج 200 طبق (تحتاج 20 كيلو) من أصل 12 كيلو متاحة فقط، والنظام رفضها بالكامل من غير أي أثر جانبي.

# التحديث: إعادة تصميم شاملة + تصحيحات جوهرية

## 1) Tailwind CSS + Framer Motion
الواجهة كلها بقت مبنية على Tailwind (كل الكلاسات القديمة زي `.btn`, `.table`, `.modal-card` اتحولت لـ `@layer components` باستخدام `@apply` — نفس الأسماء، نفس الاستخدام في JSX، بس المحرك تحت بقى Tailwind بالكامل). Framer Motion بقى بيتحكم في كل حركات الظهور/الاختفاء (المودالز، صفوف السلة، الانتقال بين الصفحات، الكاميرا).

## 2) مكوّن Modal موحّد (وإصلاح مشكلة حقيقية)
كل المودالز في النظام (فورم المنتج، التوريد، الجرد، التعبئة، الباركود، الفاتورة، التأكيد) بقت بتستخدم مكوّن `<Modal>` واحد. ده صلح مشكلة كانت موجودة فعلًا: **عرض المودال كان بالبكسل الثابت** (440px مثلًا)، فعلى شاشة موبايل أصغر من كده كان المودال بيطلع طالع بره حدود الشاشة أو لازق في الجنب. دلوقتي العرض `min(92vw, Npx)` — بيتقلص تلقائيًا وميلزقش في أي حجم شاشة، ومتمركز دايمًا في النص.

## 3) شاشة الكاشير: اختيار طريقة العرض
تابات جديدة فوق شاشة البيع: **"الباركود"** (سكانر بس) / **"المنتجات"** (تصفح وضغط بس) / **"الاثنين معًا"** (الاتنين مع بعض، الوضع الافتراضي). السكانر الفعلي شغال في الخلفية في كل الأوضاع الثلاثة.

## 4) الحذف الفعلي بدل التعطيل
"حذف منتج" دلوقتي بيشيله فعليًا من قاعدة البيانات (مش بس `isActive: false` زي قبل كده). مع حماية: لو المنتج ده خامة لمنتج تاني (زي جبنة سايبة مربوطة بطبق جبنة)، النظام بيرفض الحذف ويقولك إيه المنتجات المرتبطة، عشان متكسرش ربط موجود بالغلط.

## 5) تصحيح حساب سعر الشراء عند التوريد (تصحيح جوهري)
**المشكلة اللي كانت موجودة**: كل ما تورّد كمية جديدة بسعر مختلف، النظام كان بيمسح سعر الشراء القديم بالكامل ويحط السعر الجديد بس — يعني لو عندك 100 قطعة بـ10ج.م وورّدت 20 قطعة بـ16ج.م، النظام كان بيقول التكلفة بقت 16ج.م لكل الـ120 قطعة، وده غلط.

**الحل**: **متوسط سعر الشراء المرجّح (Weighted Average Cost)** — بياخد في الاعتبار الكمية القديمة وسعرها + الكمية الجديدة وسعرها. في المثال فوق: (100×10 + 20×16) ÷ 120 = **11ج.م**، مش 16. **تم اختبار الحساب فعليًا** بأكتر من سيناريو (كميات متساوية وغير متساوية) والنتايج مطابقة تمامًا للحساب اليدوي الصحيح.

## 6) صفحة فواتير مستقلة + تفاصيل كاملة
"الفواتير" في القائمة الجانبية — كل الفواتير بترقيم صفحات، ودوسة على أي فاتورة بتفتح تفاصيلها كاملة (كل صنف، السعر، الكمية، الخصم، الضريبة، التكلفة، صافي الربح، طريقة الدفع، المبلغ المدفوع والباقي).

## 7) تقرير "الأكثر مبيعًا"
في صفحة التقارير، جدول جديد بيوريك أكتر المنتجات مبيعًا (بالكمية والإيراد والربح) خلال فترة تختارها (7/30/90 يوم).

## 8) سجل حركة المخزون لكل منتج
زرار **"السجل"** جديد على كل منتج — بيوريك كل حركة حصلت عليه (بيع، توريد، تعديل، جرد) بالتاريخ ومين عملها والكمية قبل وبعد. ده كان موجود في الباك اند من الأول بس مكنش متاح في الواجهة.

## 9) الاستجابة على كل أحجام الشاشات
القائمة الجانبية بقت بتتحول لشريط أفقي فوق على الموبايل والتابلت (كانت بتفتقد للتحويل ده بعد إعادة كتابة الـ CSS، تم اكتشافه وإصلاحه). باقي الصفحات (الجداول، الفورمات، شاشة الكاشير) كانت بالفعل متجاوبة بـ breakpoints مناسبة من التحديث السابق.

# التحديث: RTK Query — إعادة هيكلة جلب البيانات بالكامل

استبدلنا كل نداءات `axios` اليدوية المتناثرة (كل صفحة كانت بتعمل `useState` + `useEffect` + `api.get` بنفسها) بـ **RTK Query** (من Redux Toolkit). الفايدة الحقيقية مش "كود أنضف" بس — دول تحسينات أداء فعلية:

## 1) Caching تلقائي (إلغاء تكرار الطلبات)
لو صفحتين محتاجين نفس البيانات في نفس الوقت (مثلًا شاشة الكاشير في وضع "تصفح" وصفحة "المنتجات" في تاب تاني)، **طلب شبكة واحد بس بيتبعت** ومشترك بينهم، مش طلب منفصل لكل واحدة. لو رجعت لصفحة زرتها قبل كده، البيانات تطلع فورًا من الكاش من غير ما تستنى تحميل من جديد.

## 2) تحديث لحظي مركزي بدل التكرار
قبل كده، كل صفحة كانت بتعمل `useEffect` منفصل يسمع لأحداث Socket.io وينده `reload()` بتاعتها. دلوقتي نقطة واحدة (`useRealtimeCacheSync`) بتسمع للأحداث وتنده `invalidateTags` — و**RTK Query تلقائيًا بيعيد تحميل أي بيانات شغالة فعليًا على الشاشة وعندها نفس الـ tag**، من غير أي كود إضافي في الصفحات نفسها. مثال: بيع منتج من أي كاشير بيحدّث لحظيًا: جدول المنتجات، الفواتير، ملخص التقارير، الأكثر مبيعًا — كلهم في نفس اللحظة، من غير ما أي واحد منهم "يعرف" عن التاني.

## 3) Mutations بترجع نتيجتها تلقائيًا للكاش
بعد أي عملية (إضافة منتج، توريد، تعبئة، حذف)، **مفيش أي `loadProducts()` يدوي بعد كده** — الـ mutation نفسها بتعلن إنها "غيّرت" بيانات المنتجات (`invalidatesTags`)، والجدول بيتحدث لوحده.

## تم اختبار الآلية الأساسية فعليًا (مش افتراض)
كتبنا اختبار حقيقي على الـ store نفسه (بدون متصفح) بيتأكد من:
- **الـ caching شغال فعليًا**: نفس الاستعلام مرتين = طلب شبكة واحد بس
- **الـ invalidation شغال فعليًا**: عملية إضافة منتج بتعمل refetch تلقائي لاستعلام قائمة المنتجات
- **عزل الـ tags صحيح**: عملية على المنتجات مبتعملش refetch غير ضروري لاستعلامات تانية (الفئات مثلًا)

وكمان اختبرنا `axiosBaseQuery` (الجسر بين RTK Query وaxios بتاعنا) في 3 حالات: نجاح، فشل بكود خطأ من السيرفر، وفشل شبكة كامل — والنتيجة في الحالات التلاتة صح.

## حاجة نذكرها بصراحة
الحزمة الرئيسية زادت شوية بعد إضافة Redux Toolkit + RTK Query (مكتبة معروفة بحجم معقول). الفايدة الحقيقية مش في حجم التحميل الأول، لكن في **تقليل عدد طلبات الشبكة الفعلية** أثناء الاستخدام العادي (تنقل بين الصفحات، فتح نفس الفاتورة تاني، تحديثات لحظية بدون تكرار) — وده الفرق اللي بيتحسّ فعليًا في الاستخدام اليومي، خصوصًا على إنترنت بطيء.
